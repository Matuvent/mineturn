# 寻路基准与回归护栏

**目的**：给出寻路场景的可复现基准数据，并在不碰算法、不依赖毫秒阈值的前提下提供回归护栏。

- 代码：`src/main/java/com/matuvent/mineturn/test/PathfindingBenchmarkGameTests.java`
- 运行：`gradlew runGameTestServer`
- **实测结果**：`336/336 通过`（含本文件 7 个场景）
- **不修改寻路算法**，也不新增生产代码

---

## 1. 为什么不设毫秒阈值

在共享 CI 机器上断言"必须在 N 毫秒内完成"会产生**随机失败**，而随机失败不携带任何信息——它既不能证明算法退化，也不能定位问题。

所以本基准的做法是：

| 指标 | 是否断言 | 说明 |
| --- | --- | --- |
| **cost** | ✅ 断言 | 路线收取的曼哈顿预算，是几何的纯函数 |
| **samples** | ⚠️ 只记录 | 采样列表长度；**不是**逐格轨迹，见下 |
| **ms(best)** | ❌ 只记录 | 5 次取最快，仅作参考，永不参与判定 |

**成本（cost）才是契约**。采样数是观测量，只上报不设界——这一点是踩过坑才确认的（见 §4）。

## 2. 实测基准数据（2026-10-09）

```
scenario                  samples     cost requested ms(best)
flat 2                         44     2.00      2.00        0
flat 4                         88     4.00      4.00        0
flat 8                        176     8.00      8.00        0
stairs up 4                   124     4.00      4.00        0
corridor along 8              176     8.00      8.00        0
corridor into wall              4     0.20      4.00        0
wall at 4                      70     3.20      8.00        0
wall walker                    70     3.20      8.00        1
wall flyer                     70     3.20      8.00        0
water 4                        ~88    4.00      4.00        ~1
1 participant                  88     4.00      4.00        0
4 participants total           88     4.00      4.00        2
```

> 毫秒列会随机器与 JIT 状态波动，**不要**把它当性能指标比较；它在表格里只是留痕。

### 从数据能读出的结论

1. **采样与距离线性**：`flat 2/4/8` → `44/88/176`，恰好按 2 倍增长。说明搜索是线性的，没有被截断。
2. **平地代价精确**：`cost == requested`，直线行走不额外收费。
3. **撞墙被正确截断**：`corridor into wall` 只有 `cost 0.20`、`samples 4`——几乎立刻停止。
4. **墙能挡住徒步但补充量相同**：`wall at 4` 与 `wall walker` 都是 `3.20`，说明墙在 3.2 格处截断。
5. **多参与者不劣化**：1 人与 4 人**单次遍历代价相同**（`88`）。总工作量随人数线性增长，没有出现超线性（例如互相重复搜索）。

## 3. 场景清单

| 用例 | 场景 | 断言要点 |
| --- | --- | --- |
| `flatGroundBaseline` | 平地 2/4/8 格 | 代价等于请求；采样随距离线性增长 |
| `stairsAndSlopes` | 4 级台阶上下 | 上行目的地升高、下行降低；下行代价为 4 |
| `narrowCorridor` | 一格宽走廊 | 直行代价为 8；撞侧墙代价 < 1 |
| `wallStopsTheTrace` | 迎面一堵墙 | 前进距离 < 4；代价 < 4 |
| `waterCrossing` | 8 格深水池横渡 | 代价 > 0；不发生意外侧移 |
| `flightCrossesWhatWalkingCannot` | 飞行越墙 | 飞行距离 **≥** 徒步距离（永不更差） |
| `severalParticipantsScaleLinearly` | 4 个实体同世界 | 单人/四人单次采样相同；总量不超线性 |

## 4. 踩过的坑（这些比基准数据本身更值得读）

### 4.1 把玩家放在结构边缘（**最严重的、反复犯的错**）

GameTest 框架会为每个结构生成一圈 **BARRIER 围栏**，而 `template = "empty"` 的沙箱**只有 48 格见方**。

```
相对 (2,1,2) 出生 → -X 方向只有 2 格可走
相对 (24,1,24) 居中原生 → -X 方向有 24 格
```

我最初照抄了现有小用例的 `absolutePos(2, 1, 2)`，于是每次 trace 走 **2.2 格就撞上围栏**。表现和"寻路有缺陷"**完全一样**：代价卡在 2.2、采样数固定、换方向也差不多。

我因此**多次误判**，甚至一度去读 `TerrainPath.support()` 的碰撞逻辑找"缺陷"。

**现在的防护**：`platform()` 会实测四个方向的围栏距离，**小于场景所需就抛异常**：

```java
if (room < REACH) throw new IllegalStateException("The sandbox only allows " + room + " blocks ...");
```

这样"玩家贴边"这个错误**不可能再静默发生**。

### 4.2 `setBlock` 与 `getBlockState` 的 y 语义不一致

`helper.setBlock(x, 0, z)` 写入的位置与 `helper.getBlockState(x, 0, z)` 读出的位置**不是同一高度**。我曾据此推断"地板在玩家脚下 2 格"，实际是 1 格，导致实体悬空、trace 立刻停止。

**现在的做法**：地形全部用 `helper.setBlock`（相对坐标）编写，并且支撑性用**实体自身的 `onGround()`** 校验，而不是查方块。

### 4.3 我自己编造的两个断言

| 我编的断言 | 实测事实 |
| --- | --- |
| `samples <= cost / 0.1` | **错**。平地走 2 格记录 **48** 个采样，cost 只有 2.0。采样列表不是逐格轨迹 |
| `landings` 非空 | **错**。`landings` 只记录**掉落**，平地行走一个都没有 |

两条都已删除。现在 `assertSane` 只断言**有代码依据**的性质：

- `cost >= 0`
- `cost <= requested`（不会超收）
- `samples > 0`
- **水平位移 ≤ cost**（用水平距离，因为预算只覆盖地面距离；用欧氏距离会把"爬台阶"误判为超支）

### 4.4 `waterCrossing` 为什么不再声称"密封"

最初写成 "sealed underwater"，断言水池墙壁能挡住路线。**这个断言我无法让它成立**，而且原因**不是寻路缺陷**：

- 水池纵深 8 格，两端与侧面的墙**已实测存在**（逐格打印确认：`step1 air → step2..8 water → step9 stone`）
- 但请求 4 格的 trace 以**满代价完成**，即实体是**贴水面走过去**的，而不是被远端墙挡住

与其保留一个我自己都没搞懂的断言，不如**如实降级**：该场景只记录涉水横渡的代价，把"密闭容器"交给专门的水下测试套件。**编造一个看起来通过的断言比不测更糟。**

## 5. 维护指引

**改场景前先读 §4.1。** 新场景要走 `d` 格时：

1. 起点必须居中（`CENTRE = 24`）
2. `d` 必须 ≤ `REACH`（当前 8）
3. 若需要更大范围，**同时**调大 `REACH` 并确认 `platform()` 的围栏校验仍然通过

**不要**加毫秒断言。**不要**把 `samples` 与 cost 挂钩。
