# 三叉戟拾回验收方案

**范围**：投掷三叉戟之后的回收路径 —— 忠诚 AV 返回、战内提前回收、掉落物被摧毁、满背包、
断线与重启后的实际拾回，以及**复制**风险。

> **本文件不宣称任何客户端或重启项已通过。** 自动验证部分记录的是实际 GameTest 结果；
> 需真人操作或真正重启的部分，状态一律为 `未测`。

## 设计前提（先读，决定什么能测什么不能测）

实现位于 `battle/BattleTridents.java`，有两条硬性约束：

1. **掉落物是唯一真源。** 投掷时就在落点生成真实 `ItemEntity`（`launch`），
   回收只是把这个实体里的物品转移给玩家（`recover`），**绝不重建物品**
   （`recover` 里 `drop.isAlive()` / `drop.level().getEntity(id)==drop` 双重校验）。
2. **返回任务不跨重启保存。** `returningTridents` 是 `BattleSession` 的内存列表，
   不写盘、不序列化（源码注释即"没有临时内存所有权"）。因此：

| 情形 | 结果 |
| --- | --- |
| 忠诚计时未到就退出战斗 | 走 `leave()` **提前回收** |
| 忠诚计时未到就断线 | 同"退出战斗"（断线即离场） |
| 忠诚计时未到就**关服/重启** | 返回任务消失，**物品留在世界掉落物里**；重进后需自行拾取 |
| 掉落物在返回前被销毁（岩浆/爆炸/`/kill`） | **不会重建**，物品永久失去 |

第 4 条是刻意的防复制设计，也是"没有忠诚则战后拾回"说法的由来。

## 一、自动验证（服务端 GameTest）

### 1.1 既有覆盖（已存在，非本次新增）

| 用例 | 断言 |
| --- | --- |
| `playerTridentLoyaltyAvAndUniqueReturn` | 忠诚 III 延迟 = `100/3` AV；未推进 AV 不返回；返回后原槽位组件与耐久一致、掉落物移除、`returningTridents` 清空；**重复推进/关闭不产生第二个三叉戟**（`countItem`） |
| `playerTridentLoyaltyExitAndFullInventory` | 满背包 + 占用原槽位时，退出战斗后掉落物**仍存活**并落在玩家脚边，原槽位未被覆盖 |
| `playerTridentLoyaltyDestroyedAndExitRecovery` | 掉落物先被销毁 → **不重建**（`countItem == 0`）；第二条路径：退出战斗把存活掉落物**提前回收**回原槽位 |
| `playerTridentMeleeThrowAndRecovery` | 投掷消耗一把武器、保留组件与耐久、掉落物唯一 |
| `playerTridentSpawnCancellationAndInfiniteMaterials` | 生成被取消时**不扣武器与行动**；无限材料不生成掉落物也不复制 |

### 1.2 本次新增（`test/TridentRecoveryGameTests.java`，**实际结果：4/4 通过**）

既有用例只断言 `Inventory.countItem(...)` 或"掉落物是否存活"，**都没有统计"背包 + 世界的总数"** ——
而复制缺陷恰恰表现为"多出一个 `ItemEntity`，背包里也有一个"。新增用例专门补这个盲区：

| 用例 | 断言 | 结果 |
| --- | --- | --- |
| `throwRequestSurvivesTheWireCodec` | 投掷请求经 `Request.CODEC` 往返后字段不丢（battle/revision/operation/slot/action/target/destination/previewId） | ✅ 通过 |
| `throwingCommitsExactlyOneRecoverableTrident` | 投掷后武器离开背包；**背包 + 世界总数恰为 1**；世界里恰有 1 个掉落物；**重复发送同一投掷请求不会产生第二个** | ✅ 通过 |
| `battleCloseRecoversTheDropWithoutDuplicating` | 原槽位空 → 退出战斗把掉落物**回收进原槽位**、实体移除、**总数仍为 1** | ✅ 通过 |
| `recoveryMovesToFreeBagSlotWithoutDuplicating` | 原槽位被占用但背包有空位 → 回收到背包空位、实体移除、占用槽位未被覆盖、**总数仍为 1** | ✅ 通过 |

> 运行口径：`gradlew runGameTestServer` → **317 项运行，1 项失败**。
> 失败项为 `ContactGameTests.removedfloorstopsoldgroundroute`（寻路方向、Codex 在途工作），
> **与本文件范围无关**，本次 4 个用例全部通过。

### 1.3 用例无法覆盖的（不要误以为已测）

- 断线**重连**：GameTest 里的玩家是模拟连接，不具备真实的断线/重连生命周期。
- 真正**关服重启**：GameTest 不重启服务器，"返回任务消失而掉落物留存"必须在真机上验证。
- 掉落物被**环境**摧毁（岩浆、爆炸、仙人掌）：测试用 `discard()` 模拟，等价于"实体消失"，
  但不代表各环境伤害源都已被审计。
- 实际**拾取**动作（走上去捡起）：涉及原版拾取延迟与 `setTarget`，需真人验证。
- 客户端返回**动画**（`CombatVisuals.flight`）的观感。

## 五、复制风险清单（重点盯这几处）

| 风险 | 现有防护 | 验证方式 |
| --- | --- | --- |
| 返回任务重复触发 | `returningTridents.removeIf` 一次性移除 | `playerTridentLoyaltyAvAndUniqueReturn` + 新增 C11 |
| 掉落物被销毁后重建 | `recover` 校验 `drop.isAlive()` 与 `getEntity(id)==drop` | `...DestroyedAndExitRecovery` + C8–C10 |
| 背包已有一把又重新掉落一把 | 空槽位/背包/脚边三路分支，均只转移同一 stack | 新增 `battleCloseRecovers...` 与 `recoveryMovesToFreeBagSlot...`（**总数断言**） |
| 生成事件被取消仍扣物品 | `addFreshEntity` 失败即抛错，先于 `weapon.shrink(1)` | `playerTridentSpawnCancellationAndInfiniteMaterials` |
| 无限材料模式复制 | `hasInfiniteMaterials()` 时完全不生成掉落物 | 同上 |
| 重启后内存任务与掉落物并存 | 返回任务不持久化 | **R1–R3（必须真重启）** |
| 断线瞬间回收与掉落物拾取竞争 | 断线即离场 → 提前回收 | **D1–D3（必须真断线）** |
